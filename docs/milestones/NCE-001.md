# NCE-001: Nexa PE Inspector

## Objective

Create a read-only command-line utility that reports structural metadata from
Windows Portable Executable files. Inspection must never execute the input file.

## Supported initial scope

- DOS signature and PE header location
- COFF machine and section count
- PE32 and PE32+ optional headers
- Image base, entry-point RVA, and subsystem
- Section table
- Up to the first 16 standard data directories, preserving whether each address is an RVA or a file offset
- Import library and named/ordinal import metadata
- Named export metadata
- Base-relocation block and entry counts
- Human-readable and JSON reports

## Safety requirements

- Every file read is bounds-checked.
- Every non-empty section raw-data range is checked against the input file length and must begin after the PE headers.
- Overlapping section virtual-address ranges and raw-file ranges are rejected.
- The CLI reads at most 512 MiB per input file and rejects larger inputs.
- Data-directory ranges and import/export/relocation tables must fit within one file-backed header or section range; relocation blocks must identify a 4 KiB-aligned page RVA; the security directory is validated as an 8-byte-aligned file-offset table whose WIN_CERTIFICATE records have bounded lengths and 8-byte-aligned extents.
- Import DLL names, hint/name strings, and export names are bounded by their containing file-backed region.
- Integer offset arithmetic is checked where it can overflow.
- Section counts and metadata iteration are capped.
- A libFuzzer harness exercises the public parser with arbitrary byte input; CI runs a bounded fuzz smoke test on pushes, pull requests, manual dispatch, and a weekly schedule.
- Invalid and unsupported input returns a structured error.
- The inspector never maps a PE image into executable memory or calls its entry point.
- No Windows DLL is loaded as part of inspection.

## Acceptance criteria

1. `cargo fmt --all -- --check` and `cargo test --workspace --locked` pass.
2. The CLI rejects input files larger than 512 MiB before parsing.
3. Overlapping virtual and raw section ranges are rejected.
4. The fuzz harness builds and completes a bounded smoke run.
5. The security/certificate directory (index 4) is represented as a file offset, not an RVA.
6. A declared directory count cannot exceed the entries physically present in the optional header (for the supported directory range).
7. A valid PE32+ AMD64 fixture is identified correctly.
8. Truncated and malformed headers fail cleanly without panicking.
9. Section metadata is reported from the section table.
10. Import/export metadata is reported when directories are present.
11. JSON output is valid JSON.
12. The CLI explicitly reports that execution was not attempted.

## Known limitations in this first implementation

- The parser is an initial implementation and requires broader real-world fixture
  coverage and fuzz testing before being treated as hardened.
- Synthetic fixtures cover PE32+ AMD64 and PE32 x86 optional-header parsing; broader real-world PE32 coverage is still required.
- Bound imports, delay-load edge cases, forwarded exports, and every architecture-specific detail are not yet fully interpreted. Certificate record framing and bounds are checked, but certificate payloads and signatures are not decoded or cryptographically verified.
- This milestone does not load or run programs.

## Commands

```sh
cargo test --workspace
cargo run -p nexa-inspect -- inspect ./sample.exe
cargo run -p nexa-inspect -- inspect --json ./sample.exe
```


## Additional hardening validation

Run the normal checks:

```sh
cargo fmt --all -- --check
cargo test --workspace --locked
cargo run --locked -p nexa-inspect -- --help
```

The fuzz target is isolated under `fuzz/` and can be run with a nightly Rust
toolchain and `cargo-fuzz` installed:

```sh
cargo install cargo-fuzz --locked
cargo fuzz run inspect -- -max_total_time=60 -print_final_stats=1
```

GitHub Actions runs formatting, Linux and Windows tests, Clippy with warnings
 denied, dependency audits for both the workspace and fuzz harness, and a
60-second fuzz smoke test on pushes, pull requests, manual dispatch, and a
weekly schedule. Dependabot proposes weekly Cargo and GitHub Actions updates.
A short smoke run is useful for finding crashes, but it is not a substitute for
sustained fuzzing or real-world PE corpus testing.

# NCE-007: Application Isolation, Privacy, Account Protection, and Runtime Security

## Status

**Security design and threat-model requirements documented on `main`; no runtime security boundary is implemented by this document.** NCE-007 is a mandatory design gate before NexaOS may launch a Windows executable through NCE. The current PE inspector and image-preparation pipeline remain non-executing. This milestone does not authorize process creation, executable mappings, DLL loading, privilege changes, or application launch.

## Mission alignment

NexaOS has five co-equal long-term product requirements:

1. **Broad Windows compatibility:** run the widest practical range of modern Windows applications and games, including anti-cheat-protected multiplayer titles wherever providers and publishers offer an approved support path.
2. **Performance and efficiency:** deliver responsive operation, low avoidable CPU/RAM/storage overhead, and good behavior on modest hardware without removing useful features to improve benchmarks.
3. **Customization and usability:** provide a complete, polished, configurable desktop and predictable everyday workflows.
4. **Security and resilience:** minimize vulnerabilities and privilege, contain compromises, protect system integrity, and recover safely.
5. **Privacy and account protection:** protect users' personal files, credentials, browser sessions, gaming sessions, and private activity.

Security is not a reason to abandon compatibility, and compatibility is not a reason to weaken security. The engineering challenge is to make the supported compatibility path secure by design. If a title requires an unsupported kernel driver or a publisher-controlled exception, Nexa must pursue official support and clearly report the blocker; it must not bypass anti-cheat or silently disable host protections.

No operating system can guarantee zero vulnerabilities or universal compatibility. This milestone requires measurable defenses, adversarial validation, transparent limitations, and a vulnerability response process.

## Assets to protect

1. Host integrity: system files, package manager, kernel interfaces, boot configuration, update trust roots, and other applications.
2. User files: documents, source code, photos, downloads, removable media, and application data.
3. Account material: passwords, password-manager stores, browser cookies and session tokens, game-launcher sessions, MFA recovery material, SSH keys, API tokens, and OS keyring contents.
4. User interaction: clipboard contents, keyboard input, screen contents, microphone/camera access, and accessibility interfaces.
5. Network identity and privacy: IP/network configuration, DNS activity, account identifiers, device identifiers, and application usage metadata.
6. Compatibility state: per-app prefixes, virtual registry state, caches, imported DLLs, configuration, and saved credentials.
7. Gaming integrity: anti-cheat components, protected game processes, publisher authorization state, and online/multiplayer trust signals.

## Threat actors and untrusted inputs

The design must account for:
- A malicious or compromised Windows application running with the permissions granted to it.
- A malformed or adversarial PE file targeting the parser, image preparer, import resolver, or future loader.
- A malicious, substituted, or vulnerable DLL, plugin, installer, update, or application dependency.
- A compromised desktop-to-runtime request or a local process attempting to impersonate the launcher/runtime.
- A network attacker or hostile remote service interacting with an application.
- A compromised download mirror, package source, or update channel.
- A malicious or vulnerable compatibility component attempting to cross an application or host boundary.

The threat model assumes the host kernel and verified NexaOS security components are not already compromised. Physical access, firmware compromise, kernel vulnerabilities, and third-party account enforcement remain explicit residual risks.

## Security invariants

### 1. Least privilege and host isolation

- Windows applications run as ordinary unprivileged users; no automatic administrator/root elevation.
- A compatibility process must not inherit unnecessary file descriptors, environment secrets, host capabilities, or access to unrelated processes.
- Do not expose the complete home directory, browser profiles, password stores, SSH directories, or host keyrings by default.
- Host files and devices are exposed through narrow, user-visible grants. Grants identify the specific resource and access mode; revocation and process-exit behavior must be defined.
- Per-application state is separated by identity and storage boundary. One app must not read or modify another app's private prefix by default.
- Sandboxing uses defense in depth. A single namespace, syscall filter, path check, or UI prompt is not sufficient evidence of isolation.
- The broker and UI remain unprivileged. Any future privileged helper must have a separately reviewed, minimal protocol and narrowly enumerated operations.

### 2. Credentials and account protection

- Windows applications receive no ambient access to browser cookies, saved passwords, MFA material, password-manager databases, OS keyrings, SSH keys, or unrelated launcher sessions.
- Secrets must not be placed in command-line arguments, environment variables, diagnostic logs, crash reports, or compatibility telemetry.
- Authentication hand-off must be explicit and user-mediated. Do not silently copy credentials or browser session state into an application prefix.
- Browser profiles and game-launcher sessions remain separate from NCE application data unless a future, separately reviewed integration has explicit user consent and a documented revocation path.
- Clipboard, screen capture, microphone, camera, and input-monitoring access must be mediated by clear user intent and scoped to the requesting application where the host platform supports it.
- NexaOS must never implement keylogging, credential harvesting, stealth capture, anti-cheat evasion, or tampering with protected game processes.

### 3. Privacy by default

- No usage telemetry or cross-application tracking is enabled by default.
- Optional diagnostics require informed opt-in, disclose the categories collected, and provide a clear disable/reset path.
- Do not collect document contents, credentials, clipboard contents, keystrokes, screenshots, or full command lines for routine diagnostics.
- Diagnostic records use bounded retention, local storage by default, and redaction of tokens, usernames, home-directory paths, and other sensitive values where practical.
- Compatibility reports should use the minimum data needed to identify the application build and reproduce a technical issue. Hashes and version identifiers must not be presented as proof that an application is safe.
- Network access needed by an application must not be silently routed through an undisclosed proxy or analytics service operated by Nexa.

### 4. Executable and dependency integrity

- Inspection and preparation remain data-only until a separate implementation milestone is approved.
- Future execution must enforce a reviewed executable-memory policy, bounds checks, dependency provenance rules, and failure-atomic setup.
- Do not search arbitrary host paths for DLLs or silently substitute host libraries into an application's dependency graph.
- Downloaded runtime components and NexaOS updates require authenticated metadata and integrity verification before installation.
- Update installation must be recoverable and must not silently downgrade security policy or replace trust roots.
- Compatibility status is reported per application, version, architecture, and configuration. A successful parser test is not a trust verdict or a launch-compatibility claim.

### 5. Failure containment and transparency

- Malformed inputs, policy violations, missing dependencies, sandbox setup failures, and integrity failures fail closed.
- A failed launch must not fall back to unsandboxed execution.
- Application crashes must not crash the desktop shell or corrupt unrelated application state.
- Users receive understandable explanations of requested permissions, denied access, compatibility limitations, and security status.
- Security controls must not be silently disabled to make an application or game start.

### 6. Anti-cheat and multiplayer integrity

- Treat anti-cheat-protected games as an important compatibility target and create a provider/game requirements matrix.
- Pursue official vendor and publisher cooperation, certification, signing, or supported Linux/runtime paths wherever required.
- Only implement documented and approved integration paths. Never bypass, spoof, disable, patch, evade, or tamper with anti-cheat, DRM, protected processes, game memory, or security drivers.
- A user-mode compatibility layer cannot transparently replace arbitrary Windows kernel drivers. If a game depends on unsupported kernel behavior or publisher authorization, report it as blocked/unsupported until an approved path exists.
- Fail closed when integrity checks or required provider support are absent. Never offer an unsafe compatibility mode that disables Nexa's host protections.
- Record the exact game/provider version, hardware, driver, online/multiplayer mode, approved configuration, test date, and limitations for each result.

## Trust boundaries to design and review

| Boundary | Required property |
|---|---|
| PE file to parser/preparer | Bounded, data-only parsing; malformed input cannot execute code or panic the host process |
| Desktop UI to launcher broker | Versioned, bounded, authenticated local protocol; validated structured fields; no shell-string construction |
| Broker to application process | Unprivileged launch, minimal inherited state, explicit identity and resource policy |
| Application to host filesystem | Per-app private state plus narrow user-granted resources; path and symlink escape resistance |
| Application to other applications | No shared private prefixes, process memory, credentials, or session state by default |
| Application to secrets | No ambient credential-store access; explicit, revocable user-mediated hand-off only |
| Application to devices and interaction | Scoped permission decisions for clipboard, screen, audio, camera, and input capabilities |
| Anti-cheat/provider boundary | Documented, publisher-approved integration; no tampering or evasion |
| Updater to installed system | Authenticated metadata, verified payloads, atomic/recoverable updates, rollback protection |
| Diagnostics to external destination | Off by default; explicit opt-in; minimized and redacted data |

## Required design decisions before implementation

The NCE runtime security design must document and justify:

1. Process identity and per-application isolation strategy, including how it works on the supported kernel baseline.
2. Filesystem view, home-directory confinement, removable-media access, symlink handling, and safe user-grant revocation.
3. Network access model, local socket exposure, DNS behavior, and any optional per-app network controls.
4. IPC authentication, message framing, size limits, timeouts, request correlation, cancellation, and broker crash behavior.
5. Executable-memory permissions, W^X enforcement, address-space layout, thread creation, and memory teardown.
6. DLL search order, import resolution, application-private dependencies, system DLL policy, and update integrity.
7. Credential isolation, browser/game session separation, keyring access, clipboard and screen permissions.
8. Logging, crash dumps, telemetry consent, retention, redaction, and user-accessible data deletion.
9. Security updates, signing keys, trust-root rotation, rollback protection, and recovery.
10. Anti-cheat provider requirements, official support/certification paths, kernel-driver dependencies, publisher authorization, and compatibility reporting.
11. Vulnerability disclosure, severity triage, patch SLAs, supported release windows, and incident recovery.

Candidate Linux mechanisms such as namespaces, seccomp, Landlock, cgroups, and dedicated user identities may be evaluated, but the final design must be based on the actual supported kernel and desktop environment. Do not claim a sandbox is secure merely because one mechanism is enabled.

## Staged implementation

- **NCE-007A — Threat model and data-flow inventory:** enumerate assets, trust boundaries, attacker capabilities, sensitive data flows, and residual risks.
- **NCE-007B — Unprivileged process and filesystem isolation:** prototype and test per-app identities, private state, filesystem confinement, descriptor hygiene, and fail-closed startup. No PE execution is enabled by this stage alone.
- **NCE-007C — Broker and permission protocol:** specify and test authenticated, bounded IPC, user-mediated file/device grants, cancellation, and crash isolation.
- **NCE-007D — Credential and privacy boundaries:** verify that browser profiles, keyrings, game sessions, clipboard data, and diagnostic output are not exposed without explicit authorization.
- **NCE-007E — Runtime execution review:** only after 007A–007D are accepted, design executable mappings, loader behavior, dependency policy, memory permissions, and process lifecycle. This stage requires a separate implementation proposal and approval before any real application is launched.
- **NCE-007F — Update and recovery integrity:** define authenticated update metadata, payload verification, rollback protection, recovery, and security-policy migration.
- **NCE-007G — Anti-cheat partner compatibility:** build the provider/game requirements inventory, document official support pathways, and validate only vendor- and publisher-approved configurations. No bypass or evasion implementation is permitted.
- **NCE-007H — Vulnerability response and hardening operations:** establish disclosure intake, triage, patching, supported release policy, security advisories, and recovery exercises.

Each stage is independently reviewable. Passing one stage does not imply that later stages are implemented or that the runtime is safe for general use.

## Validation requirements

Tests must run in GitHub Actions on supported Linux and Windows targets where applicable, with isolated integration tests for Linux-only sandbox controls. Required coverage includes:

- Path traversal, symlink races, descriptor leakage, inherited environment secrets, and unauthorized host-file access.
- Cross-application prefix and process isolation.
- IPC spoofing, malformed messages, oversized payloads, replay, timeout, cancellation, and broker crash.
- Secret canaries proving credentials and sensitive environment values do not appear in logs, crash artifacts, or telemetry.
- Telemetry disabled-by-default and consent/revocation behavior.
- Update signature failures, altered payloads, downgrade attempts, interrupted updates, and recovery.
- Regression tests and bounded fuzzing for every parser or protocol boundary.
- Security incident and recovery exercises, including interrupted update and compromised application containment.
- Anti-cheat compatibility validation only with provider/publisher-approved test arrangements and accounts; never attempt to defeat or bypass protections.

Tests must use synthetic fixtures and disposable test identities. Never use the user's primary browser or gaming account as a security test fixture. Never execute unknown or untrusted PE samples.

## Acceptance criteria

- A reviewed threat model and data-flow inventory exist for all listed assets and trust boundaries.
- The design identifies what NexaOS can protect, what depends on the host kernel, and what remains under third-party application/publisher control.
- No default path exposes browser cookies, password stores, MFA material, OS keyrings, SSH keys, or unrelated app sessions to a Windows application.
- Telemetry is off by default and diagnostics are minimized, bounded, and redacted.
- The runtime fails closed when isolation, dependency verification, or policy setup fails; no unsandboxed fallback exists.
- Per-application filesystem and process isolation are demonstrated by adversarial integration tests before execution is enabled.
- Credential, clipboard, screen, device, and network permissions have documented user-consent and revocation semantics.
- Update authenticity and recovery are reviewed before broad distribution.
- Anti-cheat support claims are tied to documented provider/publisher approval and reproducible tests; unsupported kernel-driver requirements are explicitly reported.
- Vulnerability disclosure, triage, patch, and recovery processes are documented and exercised.
- GitHub Actions checks pass for the exact milestone head, and limitations are documented without absolute security or account-safety claims.

## Explicit non-goals

- Guaranteeing that third-party services never suspend, flag, or restrict an account.
- Bypassing, spoofing, disabling, patching, or tampering with anti-cheat or other security controls.
- Capturing, importing, decrypting, or sharing browser/game credentials to improve compatibility.
- Running arbitrary Windows kernel drivers or granting applications host administrator privileges.
- Claiming that a permission prompt alone creates a secure sandbox.
- Claiming zero vulnerabilities, perfect security, or universal application compatibility.
- Enabling real Windows application execution as part of this design-only milestone.

## Current gate

NCE-007 is a design gate, not an implementation claim. Until the threat model and isolation design are reviewed and their acceptance criteria are met, NCE remains non-executing. The existing NCE-005 evidence gaps and NCE-006 desktop validation gates remain in force.


## Additional mandatory design requirements: authorization, deception resistance, and efficient threat detection

These requirements extend NCE-007's existing least-privilege, credential-isolation, and failure-containment invariants. They are design requirements only; they do not claim that the current preview implements these protections.

### A. Authorization must be enforced, not inferred from prompts

- A click, download, installation, broad consent screen, or acceptance of legal terms is not an unlimited grant of operating-system authority.
- Every protected capability must have an explicit policy decision tied to the requesting application identity, exact capability, resource scope, access mode, and (where appropriate) duration.
- Applications cannot grant, expand, delegate, or renew their own authority. An application cannot use one approved capability as a route to unrelated capabilities.
- Read, write, execute, delete, device, network, clipboard, screen, and credential access are distinct capabilities; granting one does not imply the others.
- Grants must be inspectable and revocable. Revocation must prevent subsequent operations and invalidate broker-side handles or leases where technically possible.
- Expired, revoked, malformed, ambiguous, or unverifiable authorization fails closed for the protected operation.
- Permission prompts must be generated by trusted NexaOS UI, identify the requesting application and publisher/provenance where known, explain the requested scope in plain language, and avoid deceptive defaults.
- A user-facing approval must never override mandatory host-integrity, cross-application, or credential-isolation boundaries.

### B. Action Guardian: mandatory policy enforcement and user explanation

Action Guardian is the proposed system-wide authorization and risk-response design, not a single UI process that acts as the security boundary.

- Mandatory enforcement belongs in kernel-supported controls and a small, separately protected policy/broker layer. UI prompts and monitoring services are not trusted enforcement boundaries.
- Sensitive operations must be denied before access when no valid authorization exists. Detection after data has already been read is not an adequate substitute.
- The policy path must be deterministic, bounded, local, and predictable. Common authorized operations must not require network reputation lookups or AI inference.
- Risk analysis may add context, alerts, or containment recommendations. It cannot silently expand permissions or authorize access to protected data.
- Responses must be proportionate: deny the specific unauthorized operation first; isolate or suspend the requesting application when evidence and risk justify it. Avoid destabilizing unrelated applications or core desktop services.
- Security events must be privacy-minimized, bounded, locally available by default, and must not record file contents, credentials, browser tokens, clipboard contents, or full sensitive command lines.
- A legitimate background service is not malicious solely because it runs without a visible window. Decisions must distinguish declared/authorized background capabilities from hidden, unauthorized access or attempts to evade policy.

### C. Deceptive links, downloads, and permission abuse

- Treat URLs, redirects, downloaded files, document content, filenames, metadata, and application-supplied descriptions as untrusted input.
- Link and download reputation checks may use signed local indicators and optional online intelligence, but core permission enforcement and isolation must work offline.
- Do not equate a valid code signature, publisher identity, reputation score, or AI classification with proof that a program is safe.
- Inspect download provenance, file type, signature status, integrity, and known threat indicators before offering execution. Keep execution disabled until the separate NCE-007E gate is approved.
- Opening untrusted content should use the relevant application's isolation boundary; a browser warning alone is not a sandbox.
- Permission requests that are unrelated to the application's declared purpose, exceed a prior grant, or target another application's private data must be denied or separately mediated.
- The UI should explain the concrete reason for a block and the affected resource, without exposing sensitive data or teaching an attacker how to evade detection.

### D. Sentinel: optional offline behavioral intelligence, never the root of trust

Sentinel is a proposed local threat-analysis component. It must complement, not replace, deterministic authorization and operating-system enforcement.

- Core protection must continue fully offline: permission checks, application isolation, credential boundaries, local event handling, and enforcement cannot depend on a remote service or model download.
- The initial implementation should prefer deterministic rules and bounded event-based behavioral features. Do not add a language model merely because AI is available; justify any model against a measured detection gap that simpler mechanisms cannot adequately address.
- If a compact local ML model is justified, load it on demand for selected suspicious events, not continuously for every file access, process event, or game frame.
- Model inference must have explicit CPU, memory, queue, and time limits. Under resource pressure, skip or defer optional analysis while preserving mandatory enforcement.
- The model and its data are untrusted inputs to the security decision. Treat application content and process-controlled strings as data, never as instructions.
- Sentinel has no direct privileged execution, permission-granting, policy-editing, or trust-root-management capability. It may return a bounded risk classification and evidence references to Action Guardian.
- Model files are immutable at runtime and integrity-verified. Model updates use authenticated, signed, rollback-protected distribution and the same recoverable update path as other security components.
- Model corruption, inference timeout, service crash, resource exhaustion, or suspected compromise must not disable the deterministic security engine or create an unsandboxed fallback.
- False positives and false negatives must be measured on documented benign and adversarial test sets. AI output must not be presented as certainty or as proof of malicious intent.
- No model training or adaptive self-modification occurs on the user's private activity by default. Any future learning feature requires a separate privacy and security review.

### E. Performance and resource acceptance

Security overhead is a product requirement and must be measured alongside protection effectiveness.

- Use an inexpensive fast path for ordinary authorized operations: kernel-enforced access checks, cached immutable identity metadata with reliable invalidation, and bounded local policy evaluation.
- Use event-driven monitoring rather than tight polling loops or continuous full-disk scans.
- Avoid repeated hashing or scanning of unchanged content. Cache only bounded, provenance-aware results and invalidate them on file change, identity change, policy change, or relevant trust-store update.
- Perform reputation lookups, deeper static analysis, and optional model inference asynchronously where doing so cannot permit a protected operation before its required authorization decision.
- Never defer a mandatory access-control decision merely to improve latency.
- Do not put AI inference, network lookups, full-file scans, or synchronous remote calls on game rendering, input, audio, or ordinary file-I/O critical paths.
- Benchmark security disabled-baseline and protected configurations on identical documented hardware and workloads. Report CPU, resident memory, storage, application launch delay, file-operation latency, event-queue delay, and gaming frame-time distributions.
- Include low-memory and CPU-pressure scenarios, cold and warm cache cases, idle operation, application startup, high-I/O workloads, and supported gaming workloads.
- Establish numerical budgets only after repeatable baseline measurements. Hosted CI results must not be represented as physical low-end hardware results.
- Performance pressure may reduce optional analysis depth or defer noncritical work; it must never disable mandatory permission enforcement, credential isolation, or application confinement.

### F. Validation scenarios

Add synthetic, disposable tests for:
- An application requesting a capability it was never granted.
- An application attempting to reuse an expired or revoked grant.
- An application trying to use a file grant to access a different path or access mode.
- A background process attempting cross-application credential or session access.
- A process attempting to expand its own permissions or impersonate another application.
- A misleading permission description or untrusted content attempting to influence a decision.
- Malformed, replayed, oversized, or delayed broker requests.
- Offline operation with no network and stale/unavailable reputation data.
- Sentinel model missing, corrupted, replaced, rolled back, timed out, resource-starved, or crashed.
- False-positive benign background services and accessibility workflows.
- CPU/memory pressure and gaming-like latency-sensitive workloads while mandatory enforcement remains active.
- Action Guardian UI failure while kernel/broker enforcement continues.

Acceptance evidence must show that unauthorized access is denied before the protected resource is disclosed, the event is explained without leaking secrets, and failure of optional intelligence does not weaken the mandatory security boundary.

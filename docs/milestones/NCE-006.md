## User outcome

A person switching from Windows should be able to use NexaOS without learning a command line for ordinary tasks. The desktop should provide a familiar taskbar/panel, application menu, file manager, settings, window management, notifications, and predictable keyboard/mouse behavior. A supported Windows `.exe` should eventually launch from a normal double-click in the file manager, with clear progress and actionable errors.

The target is minimal avoidable launch delay, not a fabricated zero-millisecond promise. Startup time, first-launch cost, warm-launch cost, CPU use, RAM use, and disk/cache growth must be measured on representative hardware before performance claims are published.

## Desktop foundation candidate

**Provisional recommendation for the first prototype: Debian 13 (Trixie) stable + the distribution-packaged LXQt 2.1 series, with Labwc evaluated as the Wayland compositor.** This is a prototype baseline, not a final product lock or a claim of verified hardware compatibility.

Reasons for this candidate:

- Debian 13 is the current stable Debian release and has a five-year support lifecycle. Its official release includes LXQt 2.1.0.
- Debian's stable repositories package the LXQt desktop, including its session, panel, runner, and PCManFM-Qt file manager. Debian describes LXQt as suitable for less powerful machines.
- LXQt is modular and provides the classic desktop building blocks Nexa needs to customize: panel, application launcher, file manager, settings, and notifications.
- Labwc is available in Debian stable as a lightweight, stacking Wayland compositor. LXQt upstream identifies Labwc as a lightweight and stable option among its supported Wayland sessions.
- Prefer the distribution's matched package set over mixing in the newest upstream desktop release. LXQt 2.5.0 raises its Qt minimum to 6.10, while Debian 13 ships Qt 6.8.2; using Debian's packaged LXQt 2.1 series avoids creating an unnecessary Qt-version mismatch.

Prototype gates before adopting this stack:

- Verify that the Debian-packaged LXQt session integration with Labwc is complete and maintainable; do not assume every upstream Wayland-session feature is packaged.
- Boot and test on a virtual machine and representative low-memory physical hardware. Measure idle RAM/CPU, login time, panel/file-manager responsiveness, and disk footprint.
- Verify graphics acceleration/fallback, suspend/resume, audio, Wi-Fi, Bluetooth, touchpad, display scaling, multiple displays, accessibility, screen locking, and recovery.
- Test XWayland behavior for legacy Linux desktop applications. This is not evidence that Windows applications or anti-cheat systems work.
- Keep a supported text-console recovery path and a fallback session available during development.
- If the prototype exposes unacceptable hardware or usability problems, compare another maintained desktop base before writing a custom shell.

The first bootable prototype should use the distribution-supported LXQt session path rather than assume the Wayland integration is already packaged. Debian's stable package index confirms LXQt 2.1 components and Labwc 0.8.3 are available, but the `lxqt-wayland-session` package documentation currently surfaced for Debian unstable, not the Debian 13 stable package set. Therefore:

- **Prototype baseline:** Debian 13 + Debian-packaged LXQt on its supported X11 session, with a lightweight window manager and display manager selected after an image build/boot test.
- **Wayland track:** evaluate Labwc separately. Promote it to the default only after the required LXQt Wayland session integration is available from a supported, maintained package source and the full login, panel, file-manager, display, input, lock, suspend/resume, and recovery paths pass testing.
- Do not treat the existence of the Labwc compositor package alone as proof of a complete desktop session.

The goal is to customize and integrate maintained components into a coherent NexaOS experience—not to fork or rewrite an entire desktop environment.

## Customization and user choice

**Product principle: lightweight by default, customizable by choice.** The default desktop is a usable starting point, never a mandatory layout or a limit on how a person works. NexaOS should let users shape their own desktop while keeping the base system lean.

Customization should cover, in progressive stages:

- **Layout:** panel/taskbar position, size, visibility, alignment, auto-hide, launcher/menu placement, desktop icons, and available workspace behavior.
- **Appearance:** wallpapers, themes, accent colors, icon sets, fonts, light/dark preference, cursor, and display scaling.
- **Workflow:** keyboard shortcuts, mouse/touchpad preferences, window focus and snapping behavior, workspaces, and user-selected startup applications.
- **Desktop arrangements:** provide sensible presets (including a Windows-familiar arrangement and a minimal arrangement) while allowing users to modify and save their own arrangement. Presets are starting points, not separate mandatory editions.
- **Optional capabilities:** let users add or disable optional desktop components through a clear settings experience. Explain meaningful storage, memory, startup, permission, or compatibility consequences before enabling components that have them.

Customization requirements:

- Store ordinary preferences per user; do not require administrator privileges for personal appearance or layout changes.
- Use documented, versioned configuration with validation and safe defaults. A malformed or unsupported preference must not prevent login; recover to a safe default and preserve recoverable user settings.
- Provide reset-to-default controls and make changes reversible. Avoid destructive migrations and never silently discard a user's configuration.
- Keep optional services and visual effects off or dormant until needed. Do not make customization depend on a heavyweight always-running daemon.
- Do not make users install a different distribution, rebuild the OS, or edit system files for ordinary desktop personalization.
- Respect accessibility preferences, keyboard-only operation, display scaling, and reduced-motion choices across themes and layouts.
- Separate user-interface preferences from security policy. Customization must never disable sandboxing, anti-cheat safeguards, updates, recovery, or other security boundaries.
- Keep the system usable if a theme, panel plugin, widget, or other optional customization component crashes or becomes unavailable. Provide a safe/default session recovery path.
- Measure the resource cost of optional features; do not claim every theme, effect, widget, or extension is free.

The first prototype need not implement every setting. It must establish a clean separation between system defaults and per-user preferences so that later customization does not require redesigning the desktop foundation.

## Scope and ordering

### 1. Desktop foundation

- Use a maintained Linux desktop/windowing foundation where practical; Nexa's value is its cohesive integration and compatibility experience, not rewriting a display server or hardware drivers.
- Provide a restrained default desktop with a panel/taskbar, app menu, file manager, settings, window controls, and notifications.
- Keep background components minimal and start optional services on demand.
- Support keyboard navigation, accessibility basics, display scaling, multiple displays, and common input devices through the host platform.
- Preserve a recovery route to a text console or known-good desktop session if shell components fail.

### 2. File association and launch UX

- Register `.exe` as a Nexa-managed file type only when the compatibility runtime is installed and available.
- Double-click must show a clear launch state and route the file to a single documented launcher interface; it must not invoke a shell command assembled from the filename or file metadata.
- Treat filenames, paths, PE metadata, icons, and embedded strings as untrusted input. Escape display text and pass paths as structured arguments, never concatenated command text.
- Provide an explicit first-run explanation for Windows applications and a per-application compatibility/status view.
- Distinguish unsupported architecture, malformed file, missing runtime component, missing dependency, permission denial, resource limit, and anti-cheat/vendor restriction.
- Do not silently retry failed launches or change system security settings to force an application to start.

### 3. Runtime integration boundary

The desktop must call a narrow launcher service/interface. It must not implement PE loading itself or bypass the NCE runtime's validation and policy checks.

The launcher interface should accept a canonical file handle/path and explicit launch options, return a request identifier and structured status, and support cancellation before process start. It must not accept arbitrary shell fragments, scripts, environment mutation directives, or privileged operations from a PE file.

The launcher must run applications with the logged-in user's privileges by default, with per-application filesystem access boundaries and explicit user consent for access outside the app's normal data area. It must not elevate privileges automatically. Crashes in an application or compatibility process must not crash the desktop or host OS.

No launcher implementation may be connected to the current `PreparedImage` API as though prepared bytes were executable. A separate, reviewed runtime/process-creation milestone is required first.

### 4. Compatibility and anti-cheat status

- Show compatibility per application, version, runtime revision, graphics stack, and anti-cheat configuration where known.
- Use only vendor- and publisher-approved anti-cheat configurations. Never bypass, spoof, disable, or tamper with anti-cheat, game memory, protected processes, or security drivers.
- If anti-cheat support is absent or unverified, warn clearly and do not present the game as safe for a primary account. If a known integrity or compatibility concern exists, fail closed rather than forcing launch.
- Never claim an account-ban-proof guarantee. Publishers control detection and enforcement; Nexa can only avoid introducing unsupported or deceptive behavior and communicate verified support accurately.

## Required implementation stages

1. Select the desktop base and document package/update/recovery strategy; prefer existing maintained components over a custom display stack.
2. Build the shell and file-manager integration without enabling Windows execution.
3. Add a mock launcher backend for UI integration tests. It must never execute supplied files.
4. Define and review the real launcher IPC contract, identity/permission model, cancellation, structured errors, and crash isolation.
5. Integrate a real runtime only after a separate milestone has established a reviewed executable-process model, memory protection policy, dependency model, and security boundary. NCE-005's evidence gates remain open and are not waived by this design.
6. Add vendor-approved anti-cheat compatibility as a separate opt-in compatibility gate, not as a side effect of generic `.exe` launching.

## Acceptance criteria

- Desktop shell starts and remains usable when the compatibility runtime is absent or crashes.
- File association and launch requests use structured paths/arguments; no shell-string construction is used.
- UI accurately represents mock states and structured failure categories without claiming execution success prematurely.
- Unsupported or unverified anti-cheat configurations are visibly distinguished and never force-launched by the shell.
- Optional components are demand-driven; idle CPU/RAM and storage costs are measured on documented hardware.
- Keyboard navigation, accessibility basics, display scaling, and common input workflows are covered.
- Recovery path is documented and tested without risking user data.
- No arbitrary PE execution is used as a desktop test fixture. UI integration tests use a mock launcher only.

## Explicit non-goals

- Reimplementing the Linux kernel, display server, GPU drivers, or a complete desktop toolkit.
- Claiming all Windows applications or games work.
- Running Windows kernel drivers through a user-mode compatibility layer.
- Bypassing anti-cheat or promising immunity from third-party account enforcement.
- Treating the current non-executable prepared PE image as a process image.
- Enabling automatic privilege elevation, disabling host security controls, or silently weakening sandbox boundaries.

## Performance principles

- Avoid an always-running heavyweight compatibility daemon when a small on-demand broker is sufficient.
- Keep shell startup independent from optional runtime initialization.
- Do not scan entire disks for executables in the background.
- Cache only bounded, invalidatable metadata; never cache executable trust decisions without revalidation.
- Measure cold and warm launch latency separately once a real, reviewed runtime exists.
- Prefer profiling and one targeted regression check over repeated broad benchmark campaigns for unrelated changes.

## Dependencies and release gates

This design may be implemented in parallel with the remaining NCE-005 evidence review, but it does not close or waive NCE-005. Real `.exe` launching remains blocked until a separate runtime milestone demonstrates safe process creation, executable-memory policy, import/dependency handling, isolation, crash containment, and recovery. Anti-cheat support remains dependent on written vendor/publisher support for the specific game and configuration.


## Current prototype: confined read-only file browser

The first built-in file-browser slice is implemented in `desktop/nexaos-welcome/nexaos_file_browser.py` and opened from the NexaOS Welcome hub.

- Starts in the logged-in user's canonical home directory; navigation is confined to that root.
- Opens directory components relative to a trusted directory descriptor with `O_NOFOLLOW`, so symbolic links cannot redirect navigation outside the allowed tree.
- Lists one directory at a time, sorts folders first, offers an explicit hidden-file toggle, sanitizes displayed names, and caps each listing at 1,000 entries.
- Is read-only: it does not create, modify, rename, delete, or open files. A folder double-click navigates; a regular file selection only updates status; a Windows `.exe` selection displays a non-execution notice.
- Does not scan whole disks, register file associations, invoke shell commands, or start user-selected programs.
- CI's headless Qt self-test creates a temporary fixture and checks folder listing, hidden-file behavior, root confinement, and UI construction.

This is a first safe browsing surface, not yet a full file manager. File operations, removable-volume navigation, Rust-controller integration, IPC, and executable launching are deliberately not included. The Python UI and Rust `DesktopController` remain separate until a reviewed interface is designed and tested.

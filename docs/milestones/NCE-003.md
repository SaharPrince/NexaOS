# NCE-003: Bounded Import and Export Resolution

## Status

**Active — typed import/export parser metadata in progress (2026-11-17).** NCE-002's non-executing image-layout foundation is accepted for engineering progression. This milestone begins isolated import/export metadata and resolution work. It does not make NexaOS ready to launch Windows applications.

## Goal

Resolve PE import requests against an explicit, caller-provided catalogue of already-inspected module exports. Produce deterministic resolution results and a validated IAT patch plan without loading DLLs, searching the host filesystem, modifying host processes, or executing Windows code.

The first target remains PE32+ AMD64. PE32 parsing remains available, but PE32 resolution is out of scope until separately specified and tested.

## Implementation progress

- **NCE-003a typed parser increment:** added typed per-import metadata alongside the legacy report, retaining import-by-name hints, effective lookup-table RVAs, IAT slot RVAs, pointer width, original first-thunk value, and first-thunk value. Name and ordinal imports remain distinct typed variants.
- Export parsing now retains the export ordinal base, every function-table slot (including zero/unused slots), name-to-function-index associations, public ordinals, optional module name, and forwarder strings as strings rather than treating them as executable RVAs.
- Legacy `imports` and `exports` fields remain present for CLI/report compatibility. Typed metadata is bounded by the existing parser ceilings (4096 thunk entries, 16384 function slots, 8192 export names, and bounded strings).
- Focused tests cover import hints/IAT locations/pointer width, PE32 ordinal imports, export ordinal base, sparse slots, and forwarders. Formatting, Clippy, and full workspace verification are pending on this parser increment.

## Existing foundation

NCE-001 already parses import libraries and symbol names/ordinals, and export names. Its current public report is intentionally compact and string-oriented. NCE-003 must preserve the existing CLI/report compatibility while introducing typed internal/public records sufficient for safe resolution:

- Import module name and descriptor metadata.
- Import lookup/IAT RVAs and pointer width.
- Import symbol as either a name (including hint where available) or ordinal.
- Export module identity, ordinal base, function-table slots, named-export associations, and function RVAs.
- Forwarder strings as forwarder metadata, not as executable addresses.

Do not infer ordinal identity from formatted strings such as `ordinal:123`. Use typed enums and checked integer fields.

## Scope and stages

### NCE-003a — typed import/export metadata

- Replace lossy internal representations with typed import/export records.
- Preserve compatibility fields in `PeReport` and existing CLI JSON unless a separately reviewed compatibility change is required.
- Retain the distinction between name imports and ordinal imports.
- Preserve export ordinal base, sparse/empty function slots, name-to-function-index associations, and forwarder strings.
- Keep all RVA/file reads bounded by validated ranges and explicit count/string limits.

### NCE-003b — pure export catalogue

- Build an immutable export catalogue from caller-supplied inspected module metadata.
- Module-name matching is case-insensitive; exported symbol-name matching follows exact, case-sensitive PE lookup semantics.
- Support name and ordinal lookups, including sparse ordinal slots.
- Do not discover modules from disk or load modules implicitly.

### NCE-003c — deterministic import resolution plan

- Resolve each import against the explicit catalogue.
- Return a structured result for every import: resolved target, missing module, missing symbol, unsupported forwarder, or malformed metadata.
- Resolve forwarders only through the same explicit catalogue, with a strict hop limit and cycle detection.
- Preserve the original IAT slot RVA and pointer width in each planned write.
- Validate every IAT destination against the planned image bounds and reject overlapping or duplicate write slots.
- Keep resolution pure: produce a patch plan; do not mutate the image buffer in this stage.

### NCE-003d — IAT patch-plan validation

- Validate the complete patch plan before any later application stage can consume it.
- Check pointer-width compatibility, destination bounds, duplicate/overlapping slots, and address arithmetic.
- Do not expose raw host pointers or arbitrary process-memory write APIs.
- Any future patch application must be a separate operation with a narrowly scoped mutable image API and all-or-nothing validation.

## Hard boundaries

- No DLL loading, host filesystem search, registry lookup, or implicit module discovery.
- No entry-point execution, thread creation, executable memory, or writable-plus-executable mappings.
- No writes to arbitrary host-process memory.
- No kernel drivers or kernel-mode compatibility.
- No silent fallback for missing modules or symbols.
- No claim of universal Windows application compatibility.
- NCE-003 does not implement the Windows x64 calling convention or Win32 APIs; those belong to later runtime milestones.

## Resource and safety requirements

- Caller-configurable ceilings for module count, export count, import count, forwarder depth, and string length.
- Checked arithmetic for all table sizes, RVAs, ordinal calculations, and IAT destinations.
- Reject malformed or ambiguous metadata with structured errors.
- No unbounded recursion; forwarder traversal must be iterative or strictly depth-bounded.
- Deterministic results independent of filesystem state or host machine.
- Keep allocations proportional to bounded metadata, not image size.

## Required tests

1. Name import resolves to the correct exact-case export.
2. Ordinal import resolves using export ordinal base and sparse function slots.
3. Missing module and missing symbol are distinct outcomes.
4. Module-name matching is case-insensitive.
5. Export-name matching remains case-sensitive.
6. Forwarder resolves through an explicitly supplied module catalogue.
7. Forwarder cycles and excessive hop depth are rejected.
8. Forwarder strings are never treated as code RVAs.
9. IAT slots outside the planned image and overlapping slots are rejected.
10. PE32+ pointer-width and arithmetic overflow cases are rejected.
11. Malformed typed records cannot panic or cause partial patch-plan output.
12. Existing NCE-001 parser, CLI JSON, NCE-002 planner/population, and workspace tests remain green.

## Exit criteria

- Typed import/export metadata is bounded and preserves PE distinctions.
- Pure resolution is deterministic against a caller-provided catalogue.
- Forwarders, missing symbols, ordinals, and IAT patch destinations are handled explicitly.
- All patch-plan validation completes before any future image mutation.
- Linux and Windows CI, formatting, Clippy, and bounded fuzz/regression tests pass.
- Documentation clearly states that resolution planning is not DLL loading or application execution.

## Deferred release gates

The broader third-party PE corpus and representative low-end hardware measurements deferred from NCE-002 remain required before real application loading is enabled. They do not block isolated, non-executing NCE-003 resolver work.

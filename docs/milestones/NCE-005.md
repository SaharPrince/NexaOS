# NCE-005: PE Compatibility and Resource-Readiness Evidence

## Status

**Scope defined; implementation and evidence collection not yet started.** This milestone is an evidence-gathering and measurement phase for the existing non-executing PE inspection and image-preparation foundation. It does not add a loader capability or change planner acceptance rules by assumption.

Baseline branch: `nce-001/pe-inspector`  
Baseline commit: `512e2515503176c1f357d511919f892a6cd1471d`

NCE-001 through NCE-004b provide the current inspection, bounded layout, image population, explicit-catalogue import resolution, symbolic IAT validation, relocation planning/application, and transactional preparation pipeline. NCE-005 addresses the deferred evidence gates retained by NCE-002, NCE-003, and NCE-004a/004b: representative PE corpus coverage and measurements on modest hardware.

## Goal

Produce reproducible, read-only compatibility evidence and honest resource measurements for the existing PE32+ AMD64 preparation stages. Use that evidence to decide whether any compatibility policy, resource ceiling, or implementation detail needs a narrowly scoped change.

The goal is not to make Windows applications launch. A prepared image remains ordinary non-executable data.

## Baseline audit

### Existing compatibility evidence

The repository currently contains:

- Synthetic parser, layout, population, import-resolution, IAT-validation, relocation, and preparation tests.
- MSVC-produced PE fixtures.
- MinGW-w64 GCC-produced PE32+ AMD64 and PE32 x86 fixtures generated in CI from repository-owned C source.
- A Clang/LLD-produced PE32+ AMD64 fixture generated in CI from repository-owned C source.
- A Windows CI `where.exe` inspection/layout check.
- Previously recorded local inspection of four Windows system executables, with section-order/adjacency observations and catalog-signature provenance checks.

This is useful engineering coverage, but it is not a diverse third-party application corpus. Operating-system samples are not redistributable project fixtures and must not be copied into the repository.

### Compatibility questions still open

1. **Section order and adjacency:** the planner rejects overlapping section destinations but does not require section-table entries to be in ascending RVA order or aligned extents to be adjacent. The PE specification describes ascending/adjacent image sections, but existing review notes correctly defer tightening acceptance until independently produced samples and supported-host behavior have been examined.
2. **Zero `VirtualSize`:** the planner explicitly falls back to `SizeOfRawData` when `VirtualSize` is zero. Existing synthetic coverage and older implementation observations do not establish how broadly current Windows versions accept this case.
3. **Unusual but legitimate layouts:** expand evidence for empty, raw-only, virtual-only, and low-section-alignment sections, plus certificate/debug data and overlays. Keep file-offset and RVA address spaces distinct.
4. **Corpus provenance:** no third-party sample should be added without its source project, exact revision/version where available, license review, architecture, and hash. A dataset's hosting license is not blanket permission to redistribute its underlying binaries.

Do not download the full Assemblage binary archive. The existing review identifies it as a multi-tens-of-gigabytes dataset whose binaries retain their originating projects' licenses. Start with metadata-only selection and retrieve only individually reviewed candidates, if access and license terms permit.

### Existing benchmark limitations

The current `nexa_image` benchmark constructs a `PeReport` directly and supplies a synthetic byte vector. It measures layout planning, image-buffer allocation, and population separately. It does not exercise PE parsing or the complete public `prepare_image` pipeline, and it has no import-bearing or relocation-bearing end-to-end case.

The PowerShell helper records the benchmark process's peak working set. This is a process-level high-water mark for a synthetic microbenchmark; it is not a process-wide heap-allocation count, a system-wide memory measurement, or a full application cold-load measurement.

### Resource-cost observation to measure, not change speculatively

The `ImageAllocator` contract requires initialized output. `SystemImageAllocator` initializes its vector to zero, and `allocate_image_buffer` then clears the returned vector again to enforce the contract for custom allocators. Population also explicitly clears planned zero-fill ranges. These writes may be redundant for the default allocator, but the custom-allocator contract and zero-initialization guarantee must not be weakened without measurements and a reviewed replacement contract.

The layout planner's temporary vectors use `Vec::with_capacity`, but parsed section count is capped at 96 and the planner also applies a caller-supplied section limit. Population range vectors use fallible reservations. Do not label these bounded small metadata allocations as an unbounded-allocation defect.

## Staged work

### NCE-005a — reproducible, license-reviewed corpus shortlist

- Inspect dataset metadata before retrieving binaries.
- Select a small, diverse set of PE32+ AMD64 candidates from unrelated source projects where practical.
- Prefer cases that exercise zero `VirtualSize`, raw-only/virtual-only/empty sections, section ordering and gaps, non-default alignments, overlays, and certificate/debug metadata.
- Verify each candidate's originating source repository, exact source revision/version where available, license, file size, architecture, and SHA-256 before local use.
- Keep third-party binaries outside the repository unless redistribution rights are explicit.
- Record a metadata-only manifest containing dataset record ID/path where applicable, provenance, license, hash, PE format/machine, alignment values, image/header sizes, section-table order and per-section ranges, certificate/debug/overlay observations, inspector/planner result, tool commit, and rejection reason.
- Run inspection and planning only. Never execute a corpus sample.

### NCE-005b — end-to-end preparation benchmark

Extend the existing diagnostic benchmark only after defining a valid, repository-owned PE fixture whose bytes are actually parsed.

Measure separately:
1. Parser-only inspection.
2. Layout planning from the parsed report.
3. Allocation-only behavior.
4. Population-only behavior.
5. Complete `prepare_image` execution with no imports and no relocation.
6. Additional import-bearing and relocation-bearing preparation scenarios if they can be represented with small deterministic fixtures and explicit catalogues.

For each run, report fixture size, image size, section count, copy/zero-fill bytes, iteration count, elapsed time, and image-buffer allocator calls. Clearly distinguish logical image-buffer allocation counts from total process heap allocations.

Use repeated runs and record the toolchain, OS build, CPU, installed RAM, power mode, iteration counts, and whether the run is cold or warmed. Keep defaults modest and configurable for low-memory systems. Retain the existing Windows process peak-working-set measurement with its limitations stated; do not present it as heap-allocation telemetry.

### NCE-005c — low-end resource baseline

- Run the same bounded benchmark on the available 4-GB-class Windows test machine and at least one Linux CI environment.
- Record CPU model, core/thread count, RAM, OS/kernel build, Rust toolchain, power mode, benchmark revision, and run configuration.
- Compare parser, planning, allocation, population, and full-preparation costs independently.
- Record process peak working set separately from logical image-buffer allocation counts.
- Do not invent a minimum RAM requirement, product-wide image-size default, latency target, or universal performance claim. Propose budgets only after results and intended workloads are reviewed.

### NCE-005d — evidence-based compatibility and cost decisions

- Review corpus results against the open questions above.
- Keep current acceptance rules if the evidence is inconclusive.
- If a change is justified, isolate it to the specific rule, add positive and negative regression fixtures, explain compatibility impact, and rerun the relevant corpus and workspace checks.
- Investigate duplicate zero-initialization only with benchmark evidence; preserve the initialized-buffer guarantee for every allocator implementation.
- Avoid broad refactors, speculative compatibility branches, and unrelated runtime work.

## Exit criteria

- A reproducible, provenance- and license-reviewed corpus shortlist exists, with no unlicensed or unclear third-party binaries committed.
- Every selected sample has a recorded SHA-256 and a read-only inspection/planning result tied to a tool commit.
- Section order/adjacency and zero-`VirtualSize` policy have an evidence-based disposition; no stricter rule is introduced solely from the specification or one implementation reference.
- The benchmark uses valid PE bytes and measures parsing plus the complete preparation pipeline, while retaining separately reported phase measurements.
- Low-end results record the environment and clearly distinguish working-set observations, logical image-buffer allocations, and process-wide allocations (the latter only if genuinely measured).
- Any implementation changes are narrow, justified by collected evidence, and covered by regression tests.
- Formatting, Clippy, workspace tests, Linux/Windows CI, fuzz smoke, and dependency audit pass on the final milestone head.
- Documentation makes no claim of universal PE compatibility, full cold-load performance, or application-launch readiness.

## Security and compatibility boundaries

NCE-005 must not introduce:

- Execution of corpus samples, mapped images, or PE entry points.
- DLL loading, host filesystem discovery, implicit module resolution, or process creation.
- IAT writes or conversion of symbolic module-relative RVAs into process addresses.
- Executable or writable-plus-executable memory, page-protection changes, or instruction-cache operations.
- Arbitrary host-process or kernel-memory writes.
- Proprietary or unclear-license binaries in the repository.
- Universal Windows compatibility claims.

The output of NCE-004b remains prepared, non-executable image data. NCE-005 does not authorize application loading, startup, or execution.

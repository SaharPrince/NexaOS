# NCE-002: PE Image Layout and Memory-Loader Design

## Status

**NCE-002 engineering foundation accepted for progression on 2026-11-17.** The pure PE32+ AMD64 layout planner, bounded non-executable image allocation, validated image population, independent plan verification, synthetic compatibility coverage, MSVC/MinGW/Clang-LLD compiler fixtures, Windows system PE checks, and benchmark instrumentation are implemented. GitHub Actions for the acceptance head `3d2b4ab` passed Rust checks (including Linux/Windows tests and compiler-fixture validation), bounded PE parser fuzz smoke, and dependency security audit.

This is an engineering milestone acceptance, not a claim of production readiness or universal Windows compatibility. Broader third-party PE corpus coverage and representative low-end hardware measurements remain deferred validation work and must be completed before enabling application loading in a later milestone.

NCE-002 is a loader foundation, not permission to execute Windows code. No entry point is called and no image page receives execute permission in this milestone.

The first implementation target is **PE32+ AMD64**. PE32 x86 remains inspectable by NCE-001 but is not part of the first memory-image implementation.

## Implemented stages

1. **Parse (NCE-001):** inspect exact file bytes and produce validated PE metadata.
2. **Plan (NCE-002a):** calculate image size, section destinations, copy ranges, zero-fill ranges, and resource requirements using checked arithmetic. No allocation or writes.
3. **Allocate (NCE-002b):** request caller-budgeted, fallible, zero-initialized, non-executable storage.
4. **Populate (NCE-002c):** copy headers and initialized section bytes and apply planned zero-fill ranges. Population consumes the buffer, so an error cannot return a partially populated image.

## Explicit non-goals

- Executing the PE entry point or transferring control to Windows code.
- Loading or resolving imported DLLs.
- Applying relocations.
- Implementing Windows process, thread, registry, COM, or Win32 APIs.
- Supporting kernel drivers, arbitrary kernel-mode code, or unsupported anti-cheat.
- Claiming compatibility with all Windows applications.
- Reserving executable memory or creating writable-and-executable mappings.
- Building a background loader daemon.

## Inputs and supported format

Initial supported target:

- Optional-header magic: PE32+ (`0x20B`).
- COFF machine: AMD64 (`0x8664`).
- Image files only; COFF object files are rejected.
- Existing NCE-001 file-size and metadata iteration limits remain in force.
- Unsupported machine types and image formats return explicit errors.

PE32 x86, ARM64, ARM, managed CLR execution, and other machine types are future work and must not be silently treated as AMD64.

## Image layout rules

- Validate `SizeOfImage`, `SizeOfHeaders`, `SectionAlignment`, and `FileAlignment` before allocation.
- `SizeOfImage` must be nonzero, bounded by a configurable caller limit, and consistent with the validated image layout.
- `SizeOfHeaders` must fit in the input and planned image.
- Every section destination range must fit entirely within `SizeOfImage`.
- Every source range must fit entirely within the input file.
- Distinct section raw-file source ranges must not overlap.
- The planner accepts a caller-configured maximum section count.
- For a nonzero `VirtualSize`, use it as the logical in-memory section extent. `SizeOfRawData` is file-aligned and may include trailing bytes beyond that extent.
- Copy `min(SizeOfRawData, VirtualSize)` bytes. Validate the complete declared raw file range against the input and against other raw ranges, even when trailing file-alignment padding is not copied into the image.
- If `VirtualSize` exceeds `SizeOfRawData`, zero-fill the remaining logical virtual extent.
- If `SizeOfRawData` exceeds a nonzero `VirtualSize`, exclude the trailing raw alignment padding from the mapped section and from copy-byte accounting.
- If `VirtualSize` is zero while `SizeOfRawData` is nonzero, retain an explicit compatibility fallback that uses the raw size as the mapped extent. This ambiguous legacy case needs additional corpus review.
- Header and section destinations must not overlap.
- Arithmetic for ranges, alignments, offsets, and totals must be checked before host-index conversion.
- The certificate/security directory is file-offset based and is not copied as a mapped image section.
- Debug and other file-only data must not be assumed to be part of the mapped image.
- For low `SectionAlignment` below 4 KiB, require `FileAlignment == SectionAlignment` and require each section with raw data to have `PointerToRawData == VirtualAddress`; synthetic positive and negative cases are covered in NCE-002e/NCE-002j.

## Memory and low-end hardware policy

The loader is demand-driven and must not run as a persistent system service.

- No image allocation until a user explicitly launches a supported application in a later milestone.
- No unbounded global image cache. The initial loader has no cache.
- Resource ceilings remain caller-configurable; product defaults wait for measurements on modest hardware.
- Reject oversized images before allocation.
- Avoid allocating a second full-size image merely to validate a completed image.
- Prefer one planned allocation and bounded scratch buffers over repeated whole-image copies.
- Release temporary buffers on every error path.
- Keep parsed metadata compact.
- Future measurements must include peak resident memory, allocation count, cold-load latency, and copy/zero-fill throughput.
- On Windows, `scripts/measure-image-bench.ps1` builds and runs the synthetic image microbenchmark and reports the benchmark process's `PeakWorkingSet64`. This is a process-level peak working-set measurement, not a full application cold-load measurement or a process-wide allocation count. Run it on each target machine and record CPU, RAM, OS build, power mode, iteration counts, and output when comparing results.
- Memory pressure must return a clear resource error rather than trigger uncontrolled retries or system-wide instability.

Do not invent RAM minimums or claim low-end performance before measurements exist.

## Memory protection and execution boundary

The image buffer is ordinary process-heap storage, zero-initialized and non-executable. Its public API exposes read-only bytes after population. It must never be simultaneously writable and executable.

NCE-002 does not call an image entry point, create a thread at an image address, or make a page executable. Final page protections and instruction-cache handling belong to a later, separately reviewed runtime milestone.

Host allocations remain inside the current Nexa process address space. The public API must not expose arbitrary host-process memory writes or caller-supplied raw pointers.

## Relocation design boundary

NCE-002 does not modify image contents for relocation. A later relocation stage must validate every block before writing, support only explicitly implemented AMD64 relocation types, validate each target's full write width, reject unsupported types, use checked arithmetic, and have positive and negative tests for each supported type.

## Error and consistency model

Return structured errors for unsupported formats, invalid alignment, invalid or excessive image sizes, out-of-bounds ranges, overlaps, arithmetic overflow, allocation failure, configured resource limits, and inconsistent plans.

Malformed or forged plans must not panic or return a partially populated image. The population stage must independently verify its input rather than assume every public plan was produced by the planner.

## Acceptance and validation

Completed and currently covered:

1. Deterministic PE32+ AMD64 layout planning.
2. Correct header and section copy placement.
3. Zero-filled virtual tails.
4. Truncated source and out-of-image destination rejection.
5. Header/section and section/section destination overlap rejection.
6. Invalid alignment and configured resource limit rejection.
7. Fallible allocator behavior and wrong-length allocator output rejection.
8. No partial image returned after population failure.
9. Population rejects out-of-bounds source ranges, overlapping destinations, and inconsistent byte accounting.
10. Population independently verifies each section's declared RVA, mapped size, copy length, zero-fill placement, and total mapped coverage.
11. Population rejects overlapping file-source ranges, including forged plans that overlap the header source range.
12. Malformed-plan tests cover mismatched copy RVA, incomplete mapped coverage, misplaced zero-fill, overlapping source ranges, arithmetic overflow, and empty section plans.
13. Raw section padding beyond a nonzero `VirtualSize` is not copied into the mapped image; unit and population tests cover the bounded copy.
14. Existing NCE-001 tests, formatting, Clippy, Linux CI, Windows CI, fuzz smoke, and dependency audit passed on commit `eb51ef9`.

Deferred beyond this milestone (required before any real application-loading release):

- Broader legitimate compiler-produced and third-party PE corpus review, especially zero-`VirtualSize` behavior and unusual section layouts.
- Benchmark runs on representative low-end hardware. The current harness is synthetic and does not measure full application cold-load behavior or process-wide heap allocations.
- Any newly discovered high-impact malformed-plan or compatibility defect must still be fixed before the affected capability is used.

CI success is not proof of exhaustive parser correctness or production readiness. The bounded fuzz smoke test is not a substitute for sustained fuzzing.

## Additional compatibility corpus review — 2026-11-16

This review records specification findings and identifies the next corpus work. It does not change loader behavior or declare NCE-002 accepted.

### Confirmed format rules

Microsoft's PE/COFF specification confirms:

- `VirtualSize` is the section's in-memory size.
- `SizeOfRawData` is initialized data on disk, must be a multiple of `FileAlignment` for images, and may exceed `VirtualSize` because raw size is rounded while virtual size is not.
- A section containing only uninitialized data should have `SizeOfRawData == 0`.
- For sub-page `SectionAlignment`, the section's file location must match its loaded RVA.
- Section headers / section data are described as ordered by ascending RVA; the specification also describes image section VAs as ascending and adjacent.

Reference: https://learn.microsoft.com/en-us/windows/win32/debug/pe-format

The current planner already handles the raw-padding and low-alignment rules above. Its explicit zero-`VirtualSize` fallback remains a compatibility policy, not a universal guarantee derived from Microsoft's current specification.

### Loader-behavior reference and limits

The corkami PE documentation describes a zero-`VirtualSize` section where `SizeOfRawData` is used. It explicitly focuses on observed loader behavior for older x86/x64 Windows versions (XP through Windows 7) and includes deliberately unusual samples. Treat it as a source of hypotheses and test cases, not as a normative specification or proof of current Windows 11 behavior.

Reference: https://github.com/corkami/docs/blob/master/PE/PE.md

### Candidate real-world corpus

Assemblage publishes Windows PE binaries built from licensed source repositories. Its dataset documentation says each binary retains the license of its originating repository, so the license must be checked per sample before use. This is a candidate source for a local, metadata-only validation corpus; it is not blanket permission to redistribute samples in NexaOS.

References:
- https://assemblagedocs.readthedocs.io/en/latest/dataset.html
- https://assemblage-dataset.net/

No downloaded binary is added to this repository. Any future corpus manifest should record the sample's source project, exact version/commit, compiler/linker when known, original license, SHA-256, architecture, and whether the sample may be redistributed. Samples remain inspection-only and must never be executed as part of parser or planner validation.

### Open compatibility questions

1. The planner rejects overlapping section destinations but does not currently require section table entries to be ordered by ascending RVA or require aligned section extents to be adjacent. Microsoft's specification describes ascending/adjacent image sections. Before enforcing this more strictly, compare independently produced and redistributable samples and determine whether any observed gaps or ordering variations are accepted by supported Windows versions.
2. Keep the zero-`VirtualSize` raw-size fallback explicit. Add real compiler-produced cases where available; do not generalize from a single synthetic fixture or the older corkami observations.
3. Continue checking unusual but legitimate combinations: empty sections, raw-only sections, virtual-only sections, section alignment near the page-size boundary, overlays, and certificate/debug data outside mapped sections.

### Current decision

No code change was justified by this documentation pass alone. The existing compiler-produced corpus (MSVC, MinGW-w64 GCC, Clang/LLD) and Windows system samples are useful but small. By the 2026-11-17 engineering decision, NCE-002 is accepted as a bounded, non-executing image-layout foundation; broader corpus evidence and representative low-end measurements are deferred release gates. NCE-003 may proceed in isolation without claiming application-loading readiness.

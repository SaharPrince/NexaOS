# NCE-002: PE Image Layout and Memory-Loader Design

## Status

**NCE-002c — bounded allocation and validated image population are implemented; current-head CI validation is pending.** NCE-002a provides a pure PE32+ AMD64 layout planner. NCE-002b adds caller-budgeted, zero-initialized, non-executable storage. NCE-002c validates every source and destination range and accounting total before copying headers/sections and applying planned zero-fill ranges. Population consumes the buffer, so failures cannot return a partially populated image.

NCE-002 defines how Nexa will transform a validated PE32+ AMD64 file into a bounded, non-executable in-memory image representation. This milestone is a loader foundation, not permission to execute Windows code. No entry point is called and no image page receives execute permission in NCE-002.

The first implementation target is **PE32+ AMD64**. PE32 x86 remains inspectable by NCE-001 but is not part of the first memory-image implementation.

## Goals

- Convert file-backed PE sections into a correctly laid-out image representation.
- Zero-fill virtual section tails where `VirtualSize` exceeds `SizeOfRawData`.
- Validate image and section ranges before allocating or copying.
- Keep allocation bounded and fail cleanly when resource limits are exceeded.
- Make the resulting image inspectable by tests without executing it.
- Keep parsing, layout planning, allocation, copying, relocation, and future protection changes as separate stages.
- Establish a foundation that can later support imports, ABI work, and application compatibility without forcing unnecessary always-running services.

## Explicit non-goals

- Executing the PE entry point or transferring control to Windows code.
- Loading or resolving imported DLLs.
- Applying relocations in the first layout-only implementation.
- Implementing Windows process, thread, registry, COM, or Win32 APIs.
- Supporting kernel drivers, arbitrary kernel-mode code, or unsupported anti-cheat.
- Claiming compatibility with all Windows applications.
- Reserving executable memory or creating writable-and-executable mappings.
- Building a background loader daemon.

## Inputs and supported format

The loader accepts a byte slice or bounded read-only file source plus a validated NCE PE report/parsed representation. It must not trust a caller-provided report unless it is tied to the exact input bytes and parser version; the preferred API is to parse once and pass an owned, validated image description internally.

Initial supported target:

- Optional-header magic: PE32+ (`0x20B`).
- COFF machine: AMD64 (`0x8664`).
- Image files only; COFF object files are rejected.
- Existing NCE-001 file-size and metadata iteration limits remain in force.
- Unsupported machine types and image formats return explicit errors.

PE32 x86, ARM64, ARM, managed CLR execution, and other machine types are future work and must not be silently treated as AMD64.

## Stage model

The implementation must preserve these independently testable stages:

1. **Parse:** obtain validated headers, section metadata, and required directory metadata from the exact input.
2. **Plan:** calculate image size, section destinations, copy ranges, zero-fill ranges, and required resource budget using checked arithmetic. This stage performs no allocation and no writes.
3. **Allocate:** request a bounded, non-executable image buffer from an allocator abstraction. Allocation failure is a normal structured error.
4. **Populate:** copy headers and initialized section bytes into the planned offsets; zero-fill virtual tails and any required gaps according to the chosen image-layout policy.
5. **Verify:** re-check the completed image against the plan and expose read-only inspection APIs to tests.
6. **Later milestones only:** apply supported base relocations, resolve imports, establish final page protections, and eventually enter a controlled runtime.

No later stage may be hidden inside parsing or allocation. Each stage needs its own error cases and tests.

## Image layout rules

The plan must use PE image-relative virtual addresses (RVAs), not host pointers, as its primary coordinate system.

- Validate `SizeOfImage`, `SizeOfHeaders`, `SectionAlignment`, and `FileAlignment` before allocation.
- `SizeOfImage` must be nonzero, bounded by a configurable loader limit, and consistent with the validated image layout.
- `SizeOfHeaders` must fit in the input and in the planned image.
- Every section destination range must fit entirely within `SizeOfImage`.
- Every source range must fit entirely within the input file.
- Distinct section raw-file source ranges must not overlap, even when a planner is given a manually constructed report.
- The pure planner accepts a caller-configured maximum section count as well as a maximum image size, bounding per-section planning work and output-vector capacity.
- Copy no more than `SizeOfRawData` bytes from a section.
- If `VirtualSize` exceeds `SizeOfRawData`, the remaining virtual bytes are zero-filled.
- If `SizeOfRawData` exceeds `VirtualSize`, the current planner describes copying the complete raw range and maps the larger of the raw and virtual sizes; this initial policy is covered by a regression test and still requires validation against a broader legitimate PE corpus.
- Header and section destinations must not overlap in the planned image.
- Arithmetic for all ends, alignments, and offsets must be checked in a wide integer type before converting to host indices.
- RVA zero is not automatically a valid section destination; all ranges must be validated against the image plan.
- The certificate/security directory is file-offset based and is not copied as a mapped image section.
- Debug and other file-only data must not be assumed to be part of the mapped image.

Alignment handling must follow the PE format rules, including the special low-`SectionAlignment` case where file and section alignment are constrained to match. Do not assume that all images use the common 4 KiB section alignment or 512-byte file alignment. Keep alignment validation separate from layout arithmetic so edge cases can be tested.

## Memory and low-end hardware policy

The loader must be demand-driven and must not run as a persistent system service.

- No image allocation until a user explicitly launches a supported application in a later milestone.
- No unbounded global image cache. The initial loader has no cache.
- Set an explicit maximum image allocation size and maximum aggregate temporary allocation size. Keep limits configurable for tests; choose product defaults only after representative low-end hardware measurements.
- Reject oversized images before allocation, not after partially populating memory.
- Avoid allocating a second full-size image merely to validate a completed image.
- Prefer one planned allocation and bounded scratch buffers over repeated whole-image copies.
- Release temporary buffers on every error path.
- Keep parsed metadata compact; do not retain duplicate raw-file and decoded-table copies without a demonstrated need.
- Measure peak resident memory, allocation count, cold-load latency, and copy/zero-fill throughput.
- Memory pressure must return a clear resource error rather than trigger uncontrolled retries or system-wide instability.

Do not invent RAM minimums or claim low-end performance before measurements exist. Benchmark on documented modest hardware and compare against a stable baseline.

## Memory protection and execution boundary

NCE-002's image buffer is **read/write and non-executable** for population and verification. It must never be simultaneously writable and executable.

The design must not call an image entry point, create a thread at an image address, or make a page executable. Final page protections and instruction-cache handling belong to a later, separately reviewed runtime milestone after relocation and import resolution are designed and tested.

Host allocations must remain inside the current Nexa process address space. Do not expose arbitrary host-process memory writes or accept caller-supplied raw pointers in the public API.

## Relocation design boundary

The first NCE-002 implementation records relocation metadata and reports whether the image appears to have relocation data; it does not modify image contents.

A later relocation stage must:

- Validate the relocation directory and every block before writing.
- Support only explicitly implemented relocation types for the target machine.
- Validate each relocation target's full write width against the planned image.
- Reject unsupported relocation types instead of guessing.
- Use checked arithmetic for the relocation delta and target value.
- Require relocations when the chosen base differs from the preferred image base, unless a separately documented policy proves the image can load at its preferred base.
- Have positive and negative tests for each supported relocation type.

## Error model

Return structured errors for at least:

- Unsupported machine or optional-header format.
- Invalid or inconsistent alignment.
- Zero, undersized, or excessive image size.
- Header range outside the file or image.
- Section source or destination range outside bounds.
- Overlapping planned image ranges.
- Arithmetic overflow.
- Allocation failure or configured resource limit exceeded.
- Unsupported image feature.
- Internal plan/population consistency failure.

Malformed input must not panic, abort the process, or leave a partially initialized image accessible as valid output.

## Test and acceptance plan

NCE-002 is not complete until all of the following are automated:

1. Valid PE32+ AMD64 headers produce a deterministic image plan.
2. A section with raw bytes copies to the correct RVA.
3. A section with `VirtualSize > SizeOfRawData` has a zero-filled tail.
4. Headers are copied only within validated `SizeOfHeaders`.
5. Multiple sections are placed at their planned RVAs.
6. Truncated raw data is rejected before allocation or copying.
7. A section destination outside `SizeOfImage` is rejected.
8. Header/section and section/section destination overlaps are rejected.
9. Invalid alignment and arithmetic overflow are rejected.
10. Oversized image plans fail before allocator invocation.
11. A deliberately failing test allocator returns a structured allocation error.
12. Error paths do not expose a partial image as successful output.
13. Output memory is non-executable; tests verify the allocator contract without executing the image.\n14. Population rejects forged/out-of-bounds source ranges, overlapping destinations, and inconsistent byte accounting before writing.
14. The existing NCE-001 test suite, Clippy, formatting, Linux CI, Windows CI, fuzz smoke, and dependency audit remain green.
15. Benchmark output records image size, peak temporary memory, allocation count, and load-plan/population time for documented fixtures.

Use synthetic fixtures and redistributable compiler-produced samples. Do not add proprietary binaries or samples with unclear redistribution rights to the repository.

## Implementation sequence

- **NCE-002a:** introduce validated PE32+ image metadata and a pure layout planner. The initial implementation is present; finish CI and broaden fixture review. No allocation.
- **NCE-002b:** add a bounded allocator abstraction and zero-initialized, non-executable image buffer. Implemented; current-head CI validation is pending. Allocation is fallible, caller-budgeted, and returns no buffer on error.
- **NCE-002c:** populate headers and sections, including zero-fill behavior, only after NCE-002b passes CI.
- **NCE-002d:** add plan verification, malformed-input tests, resource-limit tests, and benchmark instrumentation.
- **NCE-002e:** review real-world fixtures and document unsupported PE variations before considering relocation implementation.

Each substage must pass CI before the next one begins. Do not combine layout, relocation, import resolution, and execution into one large change.

## Reference

- Microsoft, [PE Format](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format): optional-header fields, section alignment, image size, section raw data, and base-relocation format.

This design is based on the published PE format documentation, but compatibility decisions must also be tested against legitimate compiler-produced and third-party PE files. The Microsoft document itself notes that it is not guaranteed to be a complete specification in every respect.
